import Roost

@main
struct Hello: RoostApp {
    @RouteBuilder
    var routes: [Route] {
        GET("/", PageController.self, .home)
    }
}

struct PageController: Controller {
    enum Action: String, ControllerAction { case home }

    static func action(_ action: Action) -> Plug {
        switch action { case .home: home }
    }

    static func home(_ conn: Connection) async throws -> Connection {
        conn.text("Hello, Roost.")
    }
}

Ownership travels with the query.

The context takes a repository and an authenticated scope. Reads stay inside the current user’s collection.

BookmarksContext.swift · excerpt 
func listBookmarks(scopeId: UUID) async throws -> [Bookmark] {
    try await repo.query(Bookmark.self)
        .where({ $0.userId == scopeId })
        .orderBy(\.createdAt, .asc)
        .all()
}

BUILT IN THE OPEN

Roost is in active development. Here’s where things stand.

A Phoenix-inspired framework.
A Swift-shaped future.

The goal is a connected development experience for server-side Swift: from the first route to an app you can understand and keep growing.

Follow development on GitHub ↗
What works today?+

Roost 2.4.0 supports generated authentication, scoped CRUD, HTML and JSON controllers, permitted parameters, form validation, per-action logs and traces, Spectro migrations, live pages, reusable form fields, key-value stores, and in-process tests. The reading-list workflow has been exercised against real PostgreSQL.

How do I get started?+

Start with Roost 2.4.0 and follow the README quickstart to generate your first app. The CLI connects routes, templates, data, and tests, with published dependencies resolved by SwiftPM.

Development prerequisites are Swift 6.3+, macOS 15+ or Linux, and PostgreSQL for database-backed apps. Roost uses Nexus 2.x (from 2.1.0), Spectro 2.x (from 2.3.1), and ESW 1.7.0; no companion checkouts are required.

View releases ↗
How close is it to Phoenix?+

Phoenix inspires the application structure, contexts, controllers, generators, and browser conventions. Routes name controller actions the compiler checks, and resources, controller plugs, and permitted parameters work as they do in Phoenix. Roost uses Swift’s type system and package tooling. Live pages use ESW Live for server-rendered HTML and interactive updates, with session ownership and CSRF protection. Roost does not claim feature parity with Phoenix.

What’s still taking shape?+

Channels, SMTP delivery, and the PostgreSQL job store still have unfinished integration. The example uses in-memory sessions; persistent deployments can use KeyValueSessionStore with Valkey. Live page state remains process-local.
